AXiA 3D — 작업 원칙

실제로 저지른 실수에서 뽑은 재발 방지 규칙 · 2026-08-04

아래 규칙은 전부 실제로 일어난 일에서 나왔습니다. 일반론이 아니라, 한 번씩 대가를 치른 것들입니다. §1 만 읽어도 됩니다 — §2 는 왜 그런지의 근거입니다.

§1. 붙여 쓸 프롬프트

작업 전:
- 메모리와 기존 기록을 먼저 읽는다. 이미 적어 둔 함정을 다시 밟지 않는다.
- 코드를 읽고 원인을 "추론"하지 않는다. 계측하고 측정한다.

판단할 때:
- 측정하지 않은 것은 말하지 않는다. 추정치를 근거로 결정하지 않는다.
- 아무것도 안 나온 측정은 "차이 없음"이 아니라 "묻지 않았음"일 수 있다.
  무엇을 물었는지 먼저 확인한다.
- 테스트를 대상 코드와 같은 믿음으로 쓰지 않는다. 결과물을 읽는다.

바꿀 때:
- 커밋하고 나서 변형한다. `git checkout --` 로 되돌리지 않는다(백업 복사본으로).
- 한 번에 한 가지만 바꾼다. 고치는 김에 다른 걸 함께 바꾸지 않는다.
- 가드를 넣었으면 그 가드를 깨서 실패를 눈으로 본다. 통과는 증거가 아니다.
- 잡히지 않는 변이는 억지 픽스처로 메우지 말고, 왜 관측 불가인지 적는다.

끝내기 전:
- 변경이 닿는 모든 검사를 돌린다. 도구의 동작이 바뀌었으면 E2E도 돌린다.
- Playwright 전에는 반드시 빌드한다(`npm run build`). dist 는 자동으로 안 따라온다.
- 결과를 있는 그대로 보고한다. 실패했으면 실패라고, 건너뛰었으면 건너뛰었다고.

§2. 무엇을 틀렸나

측정하지 않고 말했다

  1. 추정치를 적어 두고 그걸 근거로 우선순위를 정했다 검출기의 Arc 문제를 “≈0.02 mm, 아직 값어치 없음”이라 기록했습니다. 실제로 재보니 29 mm — 세 자릿수 차이였고, 6 mm 도형이 통째로 안 보이는 크기였습니다.

    그 기록 때문에 하루 동안 “값어치 없는 항목”으로 미뤄져 있었습니다.

  2. 코드를 읽고 원인을 네 번 발표했고, 네 번 다 틀렸다 수직면 문제 / 솔리드 벽 보호 / coplanar 재유도 / Weiler-Atherton — 전부 테스트 전에 말했고 전부 계측에서 무너졌습니다. 면 생성에 backtrace 를 걸자 한 번에 나왔습니다.

    원인이 “무엇이 이걸 만들었나”일 때는 읽지 말고 계측한다.

측정했지만 아무것도 묻지 않았다

  1. 프로브가 대상 코드의 계산을 복제했다 IFC 단면 자세를 검사하는 프로브가 exporter 의 산술을 그대로 옮겨 적었습니다. 고친 뒤에도 옛 답을 보고했습니다.

    같은 믿음으로 쓴 검사는 코드와 의견이 다를 수 없다. 내보낸 파일을 읽어야 한다.

  2. 전부 0 이 나온 측정을 “차이 없음”으로 읽었다 겹친 원 장면들이 모두 si=0 이라 허용오차를 200× 조여도 답이 같았습니다. 검출기가 곡면 겹침을 아예 안 본 것이었습니다 — arrangement 가 먼저 해소했으니까.

    답이 안 변하면, 질문이 도달했는지부터 확인한다.

  3. 내 프로브가 만든 결과를 결함으로 읽을 뻔했다 clearShapes() 를 부르고 면 수가 8→14→8 로 줄어드는 걸 보고 놀랐습니다. 그 API 는 메시를 안 지우고 주인만 지웁니다. 앱 코드는 그걸 호출하지도 않습니다.

    이상한 숫자를 보면 내 계측이 만든 것인지부터 의심한다.

가드가 아무것도 붙잡고 있지 않았다

  1. “고정했다”고 커밋 메시지에 썼는데 고정되지 않았다 치환이 0번 매치했고, 테스트는 값을 출력만 하고 아무것도 단언하지 않았습니다.

    치환·삽입이 적용됐는지 확인하고 나서 그 결과를 믿는다.

  2. 픽스처가 우연히 맞게 정렬돼 변이가 통과했다 포함 관계의 큰/작은 선택을 뒤집는 변이가 테스트를 통과했습니다 — face id 가 하필 맞는 순서였기 때문입니다.

    순서는 증명이 아니다. 함수가 스스로 검증하게 만든다.

  3. 도달할 수 없는 가드를 “검증됨”처럼 두었다 안쪽 전용 가드를 지워도 3366개가 전부 통과했습니다. 두 호출자 다 그 지점에 못 갑니다.

    지우지 말고, 함수의 계약을 직접 시험한다. 그리고 도달 불가라고 적는다.

필요 이상으로 바꿨다

  1. 고치는 김에 함께 바꾼 것이 멀쩡하던 걸 깨뜨렸다 포함 처리를 넣으면서 큰/작은 선택 기준을 꼭짓점 수 → 면적으로 함께 바꿨더니, 잘 되던 “원이 옆면을 넘어감”이 거부됐습니다.

    옛 경로는 그대로 두고 새 경우만 위에 얹는다.

  2. git checkout -- 로 커밋 안 된 작업을 날렸다 변이 검증 중 되돌리려다 한 시간치 구현이 사라졌습니다. 여러 세션에서 반복

    커밋이 복구 지점이다. 변형 전에 커밋하고, 복구는 cp 백업으로.

검증을 건너뛰었다

  1. 관련 없다고 판단해 E2E 를 건너뛰었고, CI 가 잡았다 cargo·vitest·tsc 전부 초록인데 Playwright 만 실패 — 도구의 동작을 바꿨고, 실제 클릭으로 실제 도구를 거치는 건 E2E 뿐이었습니다.

    “엔진을 바꿨을 때”가 아니라 “도구가 하는 일이 바뀌었을 때” E2E 를 돌린다.

  2. 메모리에 이미 적어 둔 함정을 다시 밟았다 Playwright 는 dist/ 를 서빙하는데 TS 변경 후 빌드를 안 했습니다. 버그 없는 실패를 보고 잠시 헤맸습니다. 기록되어 있었음

    시작 전에 메모리를 읽는다. 적어 두는 것만으로는 안 밟히지 않는다.

  3. API 이름을 확인하지 않고 썼고, 오류가 삼켜졌다 getLastError()(실제는 lastError())를 부르고 ?? '' 로 감싸서, 거부 사유가 사용자에게 영영 도달하지 않았습니다. 틀린 이름을 mock 한 테스트는 통과했습니다.

    호출이 아니라 사용자에게 보이는 문자열을 단언한다.

§3. 한 줄로

통과는 증거가 아니다 초록불은 “내가 생각한 경로에서 아무 일도 없었다”는 뜻입니다. 가드를 깨서 실패를 보기 전까지, 그 가드는 아무것도 붙잡고 있지 않을 수 있습니다 — 이 저장소에서 여덟 번 그랬습니다.
